# Adopting upstream v1.1.0: Phase 0 triage table

Tracking issue: https://github.com/youngsecurity/collie/issues/10
Plan: https://github.com/youngsecurity/collie/issues/10#issuecomment-5503666758
Decision log: https://github.com/youngsecurity/collie/issues/10#issuecomment-5504303107

This is the Phase 0 deliverable: a read-only classification of every fork change that upstream
`v1.1.0` (`db17c2e`) does not already carry. Nothing was merged or branched to produce it. Every
claim below was checked against `git show upstream/main:<path>`; paths and symbols are cited so
Phase 1 and Phase 2 can be executed from this file alone.

Buckets, as defined in the plan: `upstreamed` (1.1.0 has equivalent behaviour), `superseded`
(1.1.0 rebuilt the surface so the fork change is moot), `port-needed` (fork behaviour 1.1.0 lacks;
re-apply onto upstream's structure), `fork-only-keep` (fork identity), plus `drop` (merge artefact or
fork change that is now wrong).

## 1. Headline findings

1. **The "429 fork commits" are almost entirely upstream's own 0.x history.** Of the 341
   non-merge commits in `85f777b..dev-joe`, **323 are byte-identical by `git patch-id` to commits
   in `upstream/main`**. Upstream force-rewrote `main` at v1 (its history contains repeated
   `Merge main 0.x into v1` commits), which is why hashes differ and `git cherry` fails. The
   fork's lineage contains upstream's exact `v0.36.1` release commit `96c3bc3` (upstream's tag
   `v0.36.1` points at it), so the fork is `v0.36.1` + a fork delta.
2. **The true fork delta is `git diff 96c3bc3 dev-joe`: 45 files, +1997/-365 lines**, produced by
   13 feature commits and 8 sync merges. Section 3 classifies it.
3. **Phase 1 conflicts collapse from 252 files to 25 (71 hunks) if the merge uses the right base.**
   Upstream commit `baf04ac` has a tree identical to `96c3bc3^` (the fork's pre-release 0.36.1
   state) and is an ancestor of `upstream/main`. `git merge-tree --merge-base=baf04ac dev-joe
   upstream/main` conflicts only inside the fork's own delta. Section 5 gives the mechanics.
4. **Upstream 1.1.0 cannot see a fork release tag.** `bridge/update.ts:25` `SEMVER_TAG` and `:30`
   `PRERELEASE_SEMVER_TAG` both anchor with `$` and have no `+` clause, and `cli/update.ts`
   `parseRemoteTags`/`parseApiTags` filter through them. On a `youngsecurity/collie` origin every
   `+ys.N` tag is invisible to both the banner and `collie update`. `cli/install-kind.ts:182`
   `DEFAULT_UPDATE_REPO = "AltanS/collie"` and `bridge/index.ts:546` hardcode the upstream repo
   separately. This is the `port-needed` item the decision log anticipated; section 4.2 is the
   checklist.
5. **Five of the fork's most valuable changes were authored inside sync merge `896481a`
   (adopt 0.32.0) with no feature commit or changelog line**: offline-cache hardening in
   `web/src/lib/loaders.ts`, `last-seen.ts`, `routes/root.tsx`, and the `+ys.N` update-train
   logic in `scripts/collie-ctl.sh` plus ADR 0020's fork section. They are intentional (each
   describes real fork code) and are triaged below as if they were commits.
6. **The recon's "unnamed elephant" (section 4d, harness grammars and journal adapters) is not
   fork work.** Every codex/omp/agy/grok grammar commit and every journal adapter in the fork's
   lineage is patch-identical to upstream. The only fork grammar change is two AGY commits
   (`03d7487`, `e63175a`) against a file upstream has not touched since 0.36.1.

## 2. Method (reproducible)

```sh
R=/home/devusr/github/_youngsecurity-net/collie
git -C $R fetch upstream --tags
git -C $R rev-parse 'v1.1.0^{commit}'            # db17c2e == upstream/main
git -C $R merge-base --is-ancestor 96c3bc3 dev-joe    # yes: fork carries upstream's v0.36.1 commit
git -C $R merge-base --is-ancestor 96c3bc3 upstream/main  # no: upstream rewrote main at v1
git -C $R diff --stat 96c3bc3 dev-joe             # the true fork delta (45 files)
git -C $R log --reverse --format='%h %an %s' 96c3bc3..dev-joe   # 27 fork-lineage commits
# tree-identical anchor in upstream's rewritten history:
git -C $R rev-parse '96c3bc3^{tree}' ; git -C $R log --format='%h %T' upstream/main | grep 3c6fd0d4  # none
git -C $R rev-parse '96c3bc3^^{tree}'; git -C $R log --format='%h %T' upstream/main | grep "$(git -C $R rev-parse '96c3bc3^^{tree}')"  # baf04ac
# Phase 1 forecast:
git -C $R merge-tree --write-tree --name-only dev-joe upstream/main | grep -c '^CONFLICT'                       # 252 (topological base 85f777b)
git -C $R merge-tree --write-tree --name-only --merge-base=baf04ac dev-joe upstream/main | grep -c '^CONFLICT'  # 25
```

Patch-id matching: for every non-merge commit on both sides, `git diff-tree -p -m --first-parent
<c> | git patch-id --stable`; 323 of 341 fork commits match an upstream commit. The 18 that do not
are the yousecjoe commits listed in section 3.1, the fork's own release commits, and `96c3bc3`
itself (upstream's rewritten history dropped the 0.36.1 release commit and folded its notes into
`[1.0.0]`).

#### 4.2.1 `+ys.N` port checklist (every upstream 1.1.0 location)

1. `bridge/update.ts:25` `SEMVER_TAG`, `:30` `PRERELEASE_SEMVER_TAG`: add an optional
   `(?:\+ys\.(\d+))?` group before `$`. Keep both anchored (remote refs stay untrusted). Bare
   upstream tags must remain parseable so family filtering has something to exclude.
2. `bridge/update.ts:55` `parseSemverTag`, `:71` `parsePrereleaseTag` and the `PrereleaseTag`
   interface: carry a `build`/`fork` field; `:82` `versionOfTag` and `:223` `latestReleaseTag`
   (currently `parts.join(".")`, which drops metadata) must return the dotted string the tag
   actually names, or `githubReleaseUrl(repo, "1.1.0")` links to a tag that does not exist on the
   fork.
3. `bridge/update.ts:90` `versionParts` / `:137` `compareSemver`: unanchored, so `+…` is already
   ignored. Decision D3 decides whether to add a fork-counter tie-break here or a separate
   comparator used only inside the fork family.
4. `bridge/update.ts:286` `githubReleaseUrl`: `releases/tag/v${version}` carries a literal `+`;
   verify GitHub resolves it or encode as `%2B`.
5. `bridge/index.ts:546` `updateRepo` default `"AltanS/collie"` → `youngsecurity/collie` (the
   bridge cannot import `cli/`, so this is a second, independent constant).
6. `cli/install-kind.ts:182` `DEFAULT_UPDATE_REPO` → `youngsecurity/collie`. Consumers: `:185`
   `updateRepoOf`; `cli/update.ts:264` `assertOrigin`, `:892-894`; `cli/doctor.ts:416-437`

7. `cli/update.ts:111` `parseRemoteTags`, `:755` `parseApiTags`, `:83` `ReleaseTag`, `:100`

8. `cli/update.ts:194` `planUpdate`: family filter before `releaseInMajor` / `nextMajorRelease` /
   `highestRelease`; `:222` "current" arm needs the counter-aware compare if D3 says order, or

## 5. Phase 1 mechanics (recommendation)

The decision log chose a conflict-resolving merge. Do it against the right base so the 402
already-upstreamed commits are not re-litigated:

```sh
R=/home/devusr/github/_youngsecurity-net/collie
# On the integration branch (dev-joe), make git see upstream's tree-identical commit as the
# parent of the fork's 0.36.1 release commit. Local only (refs/replace); remove afterwards.
git -C $R replace --graft 96c3bc3 baf04ac
git -C $R merge-base dev-joe upstream/main        # expect baf04ac
git -C $R merge --no-ff --no-commit v1.1.0          # 25 conflicted files, 71 hunks (section 5.1)

git -C $R commit                                    # two-parent merge commit; independent of the replace ref
git -C $R replace -d 96c3bc3
```

The resulting merge commit is an ordinary two-parent commit; the replace ref only influenced how
the 3-way base was chosen during resolution. Alternative without `git replace`: `git merge-tree

`git commit-tree <tree> -p dev-joe -p db17c2e`.

## 11. Deployment-day items (corrected after the 2026-09-03 rollout)

- Export `BUN_INSTALL` outside `.env` first.
- **Restart the bridge after the build.** `web/dist` is served from disk and goes live on the
  swap, but the running process keeps the old code until `systemctl --user restart collie` (or
  the Herdr `restart` action). The symptom of forgetting: the footer shows the new version while
  Settings reports the old one.
- **Device pairing is optional.** The recon's "run `pair` for each phone" was wrong: the write
  gate arms only once at least one device is paired, and nothing pairs itself
  (`docs/security.md`). Reads and writes work as before until you choose to pair.
- If a pack exists, upgrade the lead first, regenerate invites, and expect `warn:` skew until
  members follow.
